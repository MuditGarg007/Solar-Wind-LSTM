# Solar Wind LSTM — Progress Report
**Date:** 18 May 2026

**Project:** Geomagnetic Storm Forecasting using Deep Learning

---

## Objective

I am building a deep learning system to predict the **Dst (Disturbance Storm Time) geomagnetic index** 6 hours into the future using solar wind measurements. The goal is an early warning system for geomagnetic storms that can damage satellites, power grids, and communication systems.

---

## What I Built

### Architecture
- **2-layer Bidirectional LSTM** with a custom attention mechanism
- Input: 48-hour sliding window of 15 solar wind features
- Output: 6 Dst predictions (t+1 through t+6)
- Attention weights each of the 48 input timesteps before the final prediction

### Feature Engineering
Starting from raw solar wind parameters (Bx, By, Bz, speed, density, temperature), I engineered 15 features:

| Feature | Description |
|---|---|
| `energy` | speed × Bz (solar wind injection proxy) |
| `bz_3h`, `bz_6h`, `bz_12h` | Rolling means of Bz at 3, 6, 12-hour windows |
| `speed_3h`, `speed_6h`, `speed_12h` | Rolling means of speed at 3, 6, 12-hour windows |
| `dyn_pressure` | density × speed² (ram pressure proxy) |

### Training Setup
- Asymmetric weighted loss: moderate storms (Dst < −20 nT) penalised 5×, intense storms (Dst < −50 nT) penalised 15×
- Gradient clipping (max_norm = 1.0), early stopping (patience = 15)
- Adam optimizer, lr = 0.001, 80/20 chronological train/val split

## What I Tried That Didn't Work

I attempted four different approaches to improve storm prediction. All failed.

| Approach | What I did | Result | Why it failed |
|---|---|---|---|
| Linear recalibration | Fit `actual = a·pred + b` per step on training predictions | Helped quiet, hurt storms | Train/val bias patterns differ — one linear transform cannot fix both |
| Asymmetric directional loss | Added 2.5× extra penalty when model underpredicts during storms (effective: 37.5× on intense) | Overall RMSE 8.45 → 9.54 nT | 37.5× on 145 intense samples destabilises quiet-time learning without fixing storms |
| Oversampling | Duplicated moderate windows 4×, intense windows 15× in training | Overall RMSE 8.45 → 9.67 nT | Model memorises duplicate sequences; 15× repetition of 145 samples causes severe overfitting |
| Physics-informed features | Added 5 solar wind coupling functions (Bz_south, vBs, clock angle, epsilon, Newell Φ) | RMSE 8.45 → 8.61 nT (worse) | BiLSTM already learns these implicitly from raw inputs; explicit features add collinearity, not signal |
| Hybrid switching | Use persistence when Dst ≥ threshold, model when Dst < threshold | RMSE 7.78 → 7.98 nT (worse) | Storm onset timing mismatch — a storm peaking at −60 nT at t+6 often has Dst = −25 nT now, so it gets routed to persistence |

---

## Root Cause Analysis

After all these experiments, the root cause is clear: **data scarcity**.

- Only ~145 intense storm samples (Dst < −50 nT) exist in my validation set
- Training set has proportionally the same scarcity
- Every reweighting and sampling strategy failed because you cannot learn from what isn't there

The BiLSTM also has a **condition-dependent bias**:
- Quiet times: predicts 2.89 nT too negative (overshoots)
- Moderate storms: predicts 4.07 nT too positive (undershoots magnitude)
- Intense storms: predicts 10.55 nT too positive (severely undershoots magnitude)
- Bias grows with horizon: +0.95 nT at t+1 → +2.23 nT at t+6 (regression toward mean)

The +2.22 nT overall mean residual is misleading — it is dominated by quiet samples (91% of data).

## Critical Notes on Benchmark Comparisons

### Why TriQXNet (9.27 nT) ≠ My model (7.78 nT)

| Dimension | TriQXNet | My model |
|---|---|---|
| Forecast horizon | **t+1 only** | t+6 |
| Input data | Raw RTSW (noisy, real-time ACE/DSCOVR) | OMNI (processed, cleaned) |
| Prior Dst as input | **No** — by design | Implicitly available in 48h window |
| Missing data | 3.8–9.7% imputed | Minimal (OMNI processed) |
| Persistence comparison | **Not reported** | Reported — beats persistence only at t+6 |
| Storm-conditional breakdown | **Not reported** | Reported |

At t+1, persistence RMSE is ~2.88 nT on my dataset. TriQXNet's 9.27 nT is likely also dominated by quiet-time samples — they never show a storm-conditional table, so it is unknown how the model performs during intense events. Their own extreme event case study (Oct 2001, Dst ~ −180 nT) showed 20.33–20.86 nT RMSE, consistent with my finding that all models struggle during intense storms.

### TriQXNet's genuine contribution

TriQXNet solves a **harder operational problem**: no access to prior Dst values, raw noisy satellite streams, real-time deployment constraints. That is a legitimate engineering advance. The quantum branch adds ~4% relative improvement (9.65 → 9.27 nT) over its best classical-only configuration — modest but statistically significant (p < 0.05 via 10-fold paired t-test).

### What my work adds that published benchmarks lack

1. **Persistence baseline comparison** — no other cited paper reports this. It reveals the model only beats persistence at t+6, and only meaningfully for intense storms (+29.3% skill).
2. **Storm-conditional RMSE table** — exposes that aggregate RMSE is misleading; 91% of data is quiet where persistence already dominates.
3. **Systematic negative result documentation** — four failed improvement strategies (recalibration, directional loss, oversampling, physics features) with root-cause analysis. This prevents repeating known dead ends.
4. **Honest operational recommendation** — use persistence for t+1–t+5, model only at t+6.
